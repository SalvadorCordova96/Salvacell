# Arquitectura de Salvacel local

## 5. Bloques principales

- Interfaz local: implementaciones, componentes compartidos y utilidades de presentación en `frontend/`; la página de `app/page.tsx` es la entrada del marco y reexporta la interfaz.
- Navegación de gestión: `frontend/admin-workspace.tsx` reúne el explorador global de Datos, el catálogo/inventario y el directorio maestro de proveedores bajo Administración; `frontend/settings-workspace.tsx` conserva ajustes del taller y de la aplicación. Punto de venta se limita a vender. La vista operativa de Proveedores conserva cotizaciones/compras sin exponer el directorio maestro a cuentas no administrativas. La UI filtra destinos, pero la API vuelve a validar cada operación; `admin.manage` protege la administración, las mutaciones de catálogo y los CSV; `procurement.write` conserva las compras y `backup.manage` los respaldos JSON. Véase ADR-0032.
- API del taller: implementación HTTP en `backend/http/`; las rutas de `app/api/` son adaptadores delgados del marco. Valida operaciones normales y ofrece una importación histórica separada; `/api/health` comprueba disponibilidad sin leer la base de datos.
- Identidad y acceso: usuarios individuales y roles con permisos persistidos; las rutas privadas autentican y autorizan en backend. El alta inicial es local y la bitácora conserva el actor humano.
- Evidencia fotográfica: desde el detalle de una orden se generan tokens QR de un solo canje; el celular recibe una sesión temporal restringida y los archivos quedan en un volumen privado, fuera de rutas web públicas. La página móvil y el backend están implementados, pero la entrada LAN va en un perfil HTTPS opt-in, ligada por defecto a loopback y limitada a estáticos/canje/carga. No se habilita hasta que exista autenticación inicial, certificado confiable y firewall local.
- Base local: `db/` contiene el contrato y adaptador de persistencia PostgreSQL; las migraciones PostgreSQL se conservan separadas de las migraciones SQLite históricas. PostgreSQL vive en un contenedor y volumen exclusivos de Salvacel.
- Clientes y recepción: el perfil del cliente es la entidad compartida; una recepción puede agregar varios equipos, cada uno con orden propia, y cada orden contiene líneas de reparación repetibles. `customer_devices` mantiene identidad estable del aparato y `orders.device_id` enlaza cada visita. El enlace solo se reutiliza mediante selección explícita y validación de pertenencia al cliente; marca/modelo no fusionan identidades. Véase ADR-0025.
- Seguimiento operativo: la banda superior ofrece tarjetas contextuales solo para órdenes activas; cada tarjeta resume cliente, dispositivo, reparación y estado, y abre un modal de detalle con refacciones/cotizaciones y acciones de orden. Las solicitudes de cotización se relacionan con la reparación o con un presupuesto aún no convertido; las respuestas originales y datos estructurados quedan en el historial. Cancelaciones/devoluciones y reclamos de garantía se gestionan desde la orden.
- Asistente de voz: módulo independiente con una interfaz de capacidades de voz y un adaptador inicial para Gemini Live. El módulo de recepción expone cambios controlados del borrador; el asistente no manipula el DOM ni persiste datos directamente.
- Servicio agéntico: su código y plugin viven en `../../../Salvacel-OpenClaw/` y OpenClaw se ejecuta en su propio contenedor. El worker de Salvacel reclama mensajes elegibles y llama al hook autenticado del agente restringido; el plugin solo puede devolver propuestas por el endpoint de Salvacel. PostgreSQL no es accesible desde OpenClaw y la bandeja exige confirmación humana. WhatsApp no está conectado ni se envían mensajes.
- Chat operativo: el widget persistente visual vive en `frontend/operator-chat.tsx`; su historial de mensajes solo existe en memoria del navegador. `/api/assistant/chat` autentica al operador, arma contexto mediante la API autorizada y lo envía al agente `salvacel-operator-chat` por el hook privado. El agente solo dispone de `salvacel_operator_chat_reply`, que devuelve una respuesta tipada al callback interno y no tiene acceso SQL. El backend vincula cada callback con el turno y usuario pendientes, verifica permisos y limita apertura de órdenes/perfiles a referencias presentes en el contexto autorizado de ese turno. React ejecuta navegación, abre registros bajo la sesión vigente o prepara borradores visibles. Los formularios existentes conservan el guardado explícito y auditado; teléfono y notas de clientes solo se envían cuando se solicitan explícitamente. Véanse ADR-0026 y ADR-0027.
- Compras y recepciones: `backend/http/procurement.ts` lleva ofertas elegidas a pedidos agrupados por proveedor/moneda, registra pagos separados a proveedores y aplica recepciones parciales con costo y flete trazables. El inventario solo cambia al recibir una pieza o al transferir una pieza recibida de una reparación cancelada.
- Caja: `backend/http/cash.ts` calcula la conciliación por fecha, moneda y método desde los libros canónicos, añade salidas explícitas de gastos/retiros, programa vencimientos recurrentes sin afectar caja hasta su pago y conserva cada cierre como revisión inmutable.
- Runtime local: la app TypeScript (interfaz y API) corre en Node.js dentro del contenedor de Salvacel; PostgreSQL es un contenedor separado y no publica puerto al host.
- Borradores de formularios: orden rápida y recepción se auto guardan como JSON en `form_drafts`, cada fila con propietario autenticado. La API solo lista/modifica los del usuario actual; descartar es explícito, completar el alta borra el borrador y la lista elimina los borradores propios con 30 días sin actividad. No generan folio ni movimientos, y el código de desbloqueo no se envía ni persiste. Véase [ADR-0024](adr/0024-borradores-privados-de-formularios.md).
- Pasarela local: publica la aplicación únicamente en `127.0.0.1`; la red interna privada permite a la app comunicarse con PostgreSQL sin exponerlo al host.

## 6. Flujo de ejecución

Una orden nueva pasa por la validación estricta antes de guardarse. La carga histórica transforma la hoja sin modificarla, verifica que la base esté vacía, inserta las órdenes en el orden de sus folios y agrega únicamente los cobros y costos que la fuente permite respaldar.

El endpoint `/api/agent/supplier-messages` registra eventos con idempotencia, reconoce al proveedor por número exacto sin conservar el número completo y entrega solo solicitudes candidatas del proveedor. Si hay secretos locales y configuración, el worker de Node reclama el mensaje con un límite de tres intentos y manda contexto vigente a un hook OpenClaw con token de hook dedicado. El agente `salvacel-supplier-replies` corre en sesión aislada y solo expone el plugin que devuelve una propuesta a Salvacel. El backend revalida; una persona confirma asociación y ofertas. No se conecta WhatsApp ni se envían mensajes. La red de enlace entre app y Gateway es interna y no incluye PostgreSQL.

En el chat del operador, cada turno consulta de nuevo la API de Salvacel usando la sesión autenticada y filtra los datos antes de enviarlos. La petición al hook `POST /hooks/agent` especifica el agente permitido, una sesión aislada, `deliver: false`, clave idempotente y timeout. OpenClaw confirma estado de ejecución, no el texto final; el plugin responde a `/api/agent/operator-chat-callback` con un token separado. Ese callback solo resuelve un turno pendiente en memoria, asociado al usuario autenticado, y el servidor vuelve a comprobar permisos. Para abrir una orden o perfil, el backend solo resuelve folios/referencias incluidos en el contexto de ese turno y React vuelve a comprobar que el registro está en los datos permitidos de la sesión actual. React también presenta navegación y borradores; el asistente no simula clics, no modifica el DOM y no escribe datos. No se usa el API OpenAI-compatible del Gateway ni se entrega el token Gateway al navegador. Véanse ADR-0026 y ADR-0027.

El marco web conserva sus puntos de entrada en `app/`, que delegan a `frontend/` y `backend/http/`. El backend obtiene la conexión mediante el contrato de `db/`; la interfaz no importa ni consulta la base directamente. La app web (interfaz y API) se ejecuta como un proceso Node.js dentro de su contenedor; PostgreSQL opera en otro contenedor y solo es alcanzable por la red interna de Salvacel.

La recepción captura el cliente una vez y crea una orden independiente por equipo; las reparaciones se relacionan con esa orden. Cobros y garantía permanecen en el nivel de orden/equipo, mientras que trabajo, mano de obra y refacciones se detallan por reparación.

El operador se autentica con una cuenta individual y recibe permisos del rol asignado. La API los comprueba por solicitud; las sesiones almacenan el hash del token, expiran y pueden revocarse. La creación de la primera cuenta administrativa se realiza localmente, no mediante registro abierto. Al iniciar evidencia fotográfica, una persona autenticada genera un QR para un solo equipo; el QR se canjea una vez por una sesión breve que acepta varias imágenes dentro de límites de tamaño y cantidad. El teléfono no recibe acceso a listados ni datos del cliente. Los archivos se sirven únicamente después de autorización de la API. Los uploads se reciben por una ruta móvil HTTPS opt-in que solo permite los recursos mínimos; para LAN exige certificado confiable y su firewall queda a cargo de la operación local.

El asistente de voz recibe audio mediante una sesión Live, convierte la intención en llamadas de función y Salvacel valida cada solicitud contra una lista permitida. Las funciones solo actualizan el borrador visible de recepción mediante el estado/callbacks existentes; la persona revisa y confirma el guardado. La impresión requiere su propia decisión explícita. Gemini es un adaptador intercambiable, no dueño del dominio ni de la persistencia.

La banda prioriza visualmente órdenes por fecha prometida y ofrece acciones contextuales sin sustituir la lista de órdenes; entregadas y canceladas desaparecen de esta vista activa. Seleccionar una tarjeta abre el detalle de la orden. La aplicación permite iniciar cotizaciones desde cada reparación y desde un presupuesto sin convertirlo en orden. Cada respuesta conserva texto original y datos estructurados; las ofertas se muestran para revisión y elección humana. La bandeja duradera enlaza propuestas y mensajes originales. El worker puede solicitar interpretación a un agente OpenClaw restringido mediante hook privado y sesión aislada; mensajes ambiguos, tardíos o sin candidato siguen bajo revisión, y el agente no escribe directamente a PostgreSQL. No hay canal de WhatsApp conectado ni envío automático. Los mensajes sucesivos se agrupan visualmente mediante una ventana global de silencio configurable; sin mensajes, la solicitud no se cierra automáticamente. Cancelar una consulta no cancela la reparación; cancelar la reparación cierra las consultas pendientes. Véanse ADR-0013 a ADR-0017.

Una cancelación guarda motivo y resolución financiera; la devolución cero/parcial/total se registra como salida independiente. Los reclamos de garantía se crean y actualizan ligados a la orden original; el resultado es obligatorio al cerrar y cada cambio queda auditado.

Una oferta de proveedor elegida puede convertirse en pedido en borrador, y solo una acción humana lo marca solicitado. Las recepciones son idempotentes y transaccionales; cada línea controla cantidad pendiente, costo real y flete asignado. Los pagos de proveedor no se mezclan con pagos del cliente. Cancelar no borra lo recibido; si una pieza ya recibida deja de necesitarse, el traspaso a inventario es manual y conserva costo/procedencia. Véase ADR-0018.

El cierre de caja agrega cobros, ventas no aplicadas a órdenes, devoluciones, pagos a proveedores y salidas registradas por el taller, sin confundir categorías ni contar dos veces un abono del POS. Las reglas recurrentes crean vencimientos proyectados; solo el pago explícito registra un egreso. Cada cierre guarda esperado, contado, diferencia y revisión para que una corrección no borre el cierre anterior. Véase ADR-0019.

El resumen agrupa los movimientos por moneda y mes. El resultado aproximado resta del importe cobrado solo los costos internos conocidos y avisa cuando existen costos desconocidos.

Docker y la pasarela local sondean `/api/health`; esta ruta comprueba disponibilidad del proceso y de PostgreSQL sin leer datos del taller, y no sustituye las lecturas funcionales de `/api/taller`.

## 8. Decisiones transversales

- La aplicación general permanece accesible solo por loopback. La única excepción prevista es la entrada HTTPS opt-in de fotos, cuyo bind predeterminado también es loopback y cuya allowlist no expone las demás rutas.
- Ninguna ruta de taller permite leer o modificar datos sin una sesión individual válida; el backend aplica los permisos. La cuenta de servicio del agente no equivale a un usuario y no puede suplantar al operador.
- Las respuestas de `/api/taller` omiten módulos no autorizados y nunca incluyen hashes/salts de PIN. Exportación/restauración requiere `backup.manage`; auditoría, cambios de roles y restablecimiento de contraseñas de terceros requieren `admin.manage`. Un gestor delegado no puede conceder permisos que no posee ni editar el rol administrador. La UI oculta acciones de escritura para cuentas de solo lectura, pero la decisión de acceso permanece en la API.
- Las operaciones normales son la frontera de calidad para datos futuros.
- Las excepciones históricas quedan aisladas y no se reutilizan desde el formulario cotidiano.
- Un valor monetario ausente se representa como desconocido cuando cero cambiaría su significado.
- El catálogo conserva cada accesorio y su existencia de forma independiente. `products.glass_compatibility` guarda una nota opcional de hasta 1000 caracteres con posibles compatibilidades de vidrio templado declaradas por proveedor; es texto informativo, no una equivalencia universal ni garantía de ajuste. Búsqueda y vistas de inventario pueden mostrarlo, pero no altera ventas, SKU ni stock. Véase ADR-0029.
- El catálogo inicial se carga mediante migración idempotente 0015. `products.stock`, `products.price_cents` y `products.minimum_stock` pueden ser desconocidos (`NULL`); existencia desconocida no equivale a cero. Cada funda y vidrio templado iPhone conserva su propio SKU y mínimo de reposición inicial (3 unidades); precio/proveedor/costo quedan vacíos hasta confirmación y conteo. Punto de Venta excluye artículos sin precio positivo o conteo conocido. Véase ADR-0030.
- `products.minimum_stock` es opcional y distinto de la existencia. El catálogo alerta por accesorios activos cuyo conteo conocido sea menor o igual al mínimo; un conteo pendiente no genera una falsa alerta de cero. La compatibilidad se presenta como “Compatibilidad” y sigue siendo una nota opcional de texto libre.
- `product_suppliers` asocia cero o varios proveedores activos clasificados para accesorios con cada producto. No se crean asociaciones automáticamente. Si un proveedor ya vinculado se desactiva o cambia de clasificación, el vínculo histórico se conserva y puede retirarse al editar, pero no se puede asignar de nuevo. La orden de compra guarda el proveedor efectivamente elegido para esa compra. Véase ADR-0031.
- La procedencia de datos antiguos se conserva para evitar presentarlos como mediciones actuales exactas.
- La vigencia de garantía se deriva de la fecha de entrega y los días registrados; los términos se guardan como configuración del taller y no se inventan para órdenes antiguas.
- La identidad del cliente se conserva como perfil, no como columnas duplicadas en cada reparación; no se fusionan perfiles históricos dudosos automáticamente.
- La identidad del equipo es independiente de cada orden/visita. Las órdenes existentes se migran a identidades separadas (sin deduplicar por IMEI, marca o modelo); visitas nuevas solo comparten identidad si el operador selecciona el equipo anterior del mismo cliente. Datos físicos de la orden se conservan como captura histórica. Véase [ADR 0025](adr/0025-identidad-persistente-de-equipos.md).
- Los perfiles de cliente admiten un teléfono principal y otro opcional; ambos se buscan sin cambiar su formato de presentación. Las órdenes conservan una copia histórica de su teléfono y solo se vinculan al perfil cuando la persona lo elige explícitamente. Los números registrados no implican consentimiento ni destinatario de mensajes. Véase [ADR 0023](adr/0023-telefonos-de-contacto-del-cliente.md).
- Una cotización conserva el mensaje original y un resumen técnico opcional; proveedor, precio exacto y fecha de solicitud se registran por separado para el historial. Las variantes se mantienen como ofertas distintas y los datos desconocidos no se completan por inferencia. La ventana global de silencio configurable cierra un grupo de mensajes “por ahora” solo después de que haya llegado al menos uno; la falta total de respuesta no cancela ni vence la solicitud. Una respuesta tardía puede revisarse manualmente si la orden sigue activa; si está cancelada, queda en historial y no reactiva acciones.
- `price_requests` puede apuntar a `repair_id` o `quote_id`; `price_request_suppliers` conserva proveedores seleccionados y una referencia opaca única; `supplier_inbound_messages` conserva eventos idempotentes, propuesta, revisión y estado/reintentos del worker. `supplier_responses` conserva cada oferta estructurada y vínculo al mensaje. Pedidos, pagos de proveedor, recepciones y caja se registran en entidades separadas; migraciones `0003` a `0007` son aditivas. Los respaldos nuevos usan esquema `0026`; se aceptan respaldos anteriores. OpenClaw no puede seleccionar, comprar ni guardar ofertas: la API de Salvacel valida y requiere revisión humana.
- La migración `0007_cash_control.sql` añade libros de salidas, gastos recurrentes y cierres; los libros de pagos, ventas, reembolsos y compras siguen siendo la fuente de movimientos correspondiente. Los respaldos nuevos usan esquema `0026` e incluyen las tablas de caja, equipos y metadatos QR. Las pruebas de restauración cubren su conservación.
- Los reembolsos se registran como resoluciones financieras inmutables separadas de los cobros; los importes devueltos no pueden exceder lo cobrado vigente.
- Los reclamos de garantía son seguimientos operativos versionados y auditables; no determinan elegibilidad legal y no se borran.
- Antes de restaurar un respaldo, la API conserva una copia completa recuperable en la misma base, incluye resoluciones financieras y mantiene las cinco copias previas más recientes.
- Las tablas de identidades, roles y sesiones de operador no forman parte del respaldo funcional JSON. Este sí conserva los metadatos QR/fotos, pero revoca las sesiones temporales al restaurar; los bytes de las imágenes permanecen en el volumen privado y requieren su propio respaldo. Véase ADR-0028. La carga móvil usa una concesión temporal de alcance único y almacena archivos fuera de rutas públicas; la conectividad LAN seguirá deshabilitada hasta verificar el control completo.
- La captura móvil de fotos está implementada en código pero deshabilitada por defecto. Requiere migración de identidades/fotos, cuenta inicial, volumen privado, certificado HTTPS confiable y firewall configurado antes de su primer uso desde LAN. Véase [ADR 0021](adr/0021-evidencia-fotografica-por-qr.md) y [guía de activación](qr-photo-setup.md).
- La organización del código separa interfaz (`frontend/`), manejadores HTTP (`backend/http/`) y persistencia (`db/`) por carpetas, manteniendo fachadas del marco en `app/`. En local, la interfaz y API comparten el contenedor Node de la app; PostgreSQL es un contenedor separado tras la red interna privada.
- La base PostgreSQL no publica puerto al host ni a otros proyectos. La contraseña solo se monta como secreto local; no se incluye en la imagen.
- El volumen SQLite/D1 histórico no se elimina ni se importa automáticamente. Respaldos y restauración del motor nuevo deben seguir semántica y herramientas compatibles con PostgreSQL.
- La clave permanente de Gemini se conserva únicamente como secreto local del servidor. El navegador obtiene solo credenciales efímeras restringidas para abrir una sesión Live; ninguna instrucción configurable puede ampliar las herramientas autorizadas por código. Las pruebas de llamadas usan un adaptador falso y no requieren credenciales ni red.
